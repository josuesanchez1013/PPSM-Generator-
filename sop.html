Building a PPSM register, start to finish

How to gather network data and turn it into a Ports, Protocols and Services Management register and boundary diagram.

7 procedure steps Runs offline in a browser Safe on standalone and air-gapped systems

What this tool does

PPSM Builder is a single HTML file that turns raw network data — packet captures, firewall connection tables, NetFlow, scan output — into a Ports, Protocols and Services Management register. It identifies the systems behind the addresses, and generates a boundary diagram from the finished register.

The register answers two questions at once:

  • What ports and protocols are in use
  • Which systems are using them

An IP address on its own is not an answer to the second question. Reviewers approve traffic between named systems, and an address does not say what the system is or who owns it. Every internal endpoint needs a hostname before the register goes forward, and the tool tracks how far along you are.

On static addressing. In MOPS, MPE and CSS environments IP addresses are statically assigned, so an address does stay with a host. That makes hostname resolution easier, not optional: the register still has to name the system, because a reviewer reading 10.20.30.15 cannot tell whether it is a domain controller or a printer, and the static assignment lives in a document they do not have. Where addressing is static you also have a reliable naming source to work from, which is usually the assignment spreadsheet or the AD/CMDB export.

Runs entirely offline

Everything runs inside the browser on the machine you open it on. Nothing is uploaded, nothing is installed, and no network connection is needed. Packet captures are decoded locally. That makes it safe to carry onto a standalone or air-gapped system — copy the file over, double-click it, and work.

Scope note. The tool assembles a register and draws a picture of it. It does not certify compliance, and it does not replace your approved network architecture drawing. The accuracy of the inputs, and the boundary and classification analysis, stay with you.

Before you start

  1. Copy the .html file to a local folder you own — your Desktop is fine. Running it from a network share, a SharePoint viewer, or an email preview pane will break file reading.
  2. Open it in Edge, Chrome, or Firefox. Confirm the address bar shows a file:// path. If it opens in a document viewer instead, right-click → Open with → your browser.
  3. Click Self-Test at the top. It runs about three dozen checks against the parsers, exports, and diagram code. A green summary means the tool works on that machine. Do this once on any new or standalone system before you rely on the output.

The Self-Test runs in isolation and does not touch data you have already loaded, so it is safe to run at any point.

  6. 3b
    DNS serverExport the DNS zones
    Run it here: A DNS server, usually a domain controller — PowerShell, Run as Administrator

    Every zone, forward and reverse, with the record data expanded — a plain Export-Csv writes "DnsServerResourceRecordA" in place of the address, which is no use:

    DNS SERVER PowerShell, Run as Administrator
    Get-DnsServerZone | Where-Object { -not $_.IsAutoCreated } | ForEach-Object {
  $z = $_.ZoneName
  Get-DnsServerResourceRecord -ZoneName $z |
    Where-Object RecordType -in 'A','PTR','CNAME' |
    Select-Object HostName, RecordType, @{n='ZoneName';e={$z}},
      @{n='IPv4Address';e={$_.RecordData.IPv4Address.IPAddressToString}},
      @{n='PtrDomainName';e={$_.RecordData.PtrDomainName}},
      @{n='HostNameAlias';e={$_.RecordData.HostNameAlias}}
} | Export-Csv -NoTypeInformation dns-records.csv

    Put it in ppsm-results\inventory\. Where PowerShell is not available, dnscmd /zoneprint <zone> > zone.txt for each zone is read just as well.

    Which address matters

    A forward zone maps name → address (an A record). A reverse zone maps address → name: the owner 11.40.22.172.in-addr.arpa is the address 172.22.40.11 read backwards. Take both — the reverse zone is the authoritative answer to "what is this address called".

    Gives you: The authoritative name for every address. Reverse zones answer "what is this address called" directly, and CNAME aliases let a row that only has an alias still find its address.

Which address ends up where

Every source writes the two ends of a flow differently, and PPSM registers the listening service — never the client. One rule covers all of it: the end offering the service becomes the Destination, and whoever reached it becomes the Source. Each collection card says which column that is; this is the same thing in one place.

Addresses that point nowhere. A few values look like addresses but are not ones a register can cite, and the builder handles each rather than carrying it through:

  • 0.0.0.0 and * mean every interface on this host. They are attributed to the machine the file came from — which is why the collector writes a # ppsm-host: line, and why a Windows CSV should be named after its host.
  • 127.0.0.1 and 127.0.0.53 are loopback. A service bound only to loopback cannot leave the host, so it crosses no boundary and is not registrable. Those rows are skipped and the count is shown on the import line.
  • IPv4 only. Any IPv6 row is set aside on import and the count is shown, so a stray AAAA record or a link-local flow never reaches the register. Turn that off under Settings if the enclave really does run dual stack.
  • An ephemeral port as the destination — 32768–60999 or 49152–65535 — nearly always means the capture was read backwards. The review checks flag those rather than registering the client as a service.
  • A MAC address is not an endpoint, and a network such as 172.22.14.0/24 stays a network: it is a valid rule source, but it never gains a hostname.

What the eMASS template needs from you

The export matches the PPSM Boundary Information Import Template exactly: the same 21 columns in the same order, the same header block, and the Glossary and Instructions sheets alongside. Its own instructions say that every field except Purpose is required, so anything the collection cannot observe has to come from you. Most of it is set once and applies to every row.

Set once, under Settings

SettingFills
DNS domainSource FQDN and Destination FQDN. A short name plus your domain makes the fully qualified name the template asks for. Collecting the DNS zones is the better answer, but this covers what they miss.
Physical location of this enclaveSource and Destination Physical Location or Cloud Service Provider, for anything inside your ranges. Building, base, room — whatever your organisation uses.
Label for anything outsideThe same two columns for external addresses. A cloud provider name where that is what it is, otherwise something like External (non-DoD).

Boundary for internal rowsBoundary. The template has no plain "Internal", so internal traffic exports as one of the Internal Use Only boundaries — 18 by default.

Fill in the system header

Open eMASS template header under System Identification. These go into the block above the column headings, and none of them can be worked out from traffic: Exported By, Office / Org, Information System Owner, System ID, DITPR ID, POC name, phone and e-mail, and the Date Reviewed / Updated with who reviewed it.

Fill in per row

Purpose is the one field the template marks optional, and the one a reviewer reads first. It is the mission justification: why this flow needs to exist. Select several rows and use Bulk apply where a group shares a reason.

Everything else the export fills from what was collected. When you press Export → eMASS PPSM Template (.xlsx) the tool names any required field still empty and how many rows it affects, so you can see what is left before the workbook goes anywhere.

Do not restructure the workbook. The importer reads columns by position, and the template's own instructions say not to delete columns or sheets, remove the classification label, or add columns. The export already respects the character limits it sets — 20 for Port and Protocol, 40 for the Application/Software Record Name, 500 for Source and Destination, 750 for the FQDN and IP fields, 1500 for the location fields and 1000 for Purpose — and truncates rather than letting a row be rejected.

Formats. Anything here can arrive as CSV, as an Excel .xlsx workbook, or as a text-based PDF, and the builder identifies each file from its contents rather than its name. It will not read older binary .xls files (save them as .xlsx), scanned or image-only PDFs, or zip archives (extract them first). Read-me and notes files in the folder are skipped.

How names are cross-referenced. Every name source feeds one inventory, and that inventory is applied to every row from every file, in both directions: an address gains its hostname, a hostname gains its address, and a short name such as WSUS11 is completed to wsus11.range2.mil. Where sources disagree the most authoritative wins — reverse DNS, then forward DNS and AD, then the host itself, scans, hosts files, FMC discovery, DHCP, NetFlow labels, and ARP last — and the losing names are kept as aliases so a lookup by any of them still lands on the right host. A short name shared by two different hosts is never guessed.

2

Gather the data

Collect from the broadest source you have access to first, then fill gaps with host-level tools. Below is the exact command or path for each supported input.

Packet captures (pcap / pcapng)

A capture shows actual observed traffic rather than a point-in-time table, so it is the most detailed source available. It is also the most focused: a host capture sees only what crosses that one interface.

When to reach for a host capture. Running tcpdump or pktmon on an endpoint is the right call when none of the other collection points sit in a physical location that can see the traffic you are after. A NetFlow collector or a firewall only observes what routes through it, so an east-west flow between two hosts on the same switched segment never appears there. If the flow you need is not showing up in NetFlow or the firewall connection table, that is the signal to go capture it on the host itself.

LINUX HOST the host you want to capture ontcpdump
tcpdump -i eth0 -nn -s0 -w capture.pcap
WINDOWS HOST the host you want to capture onpktmon — built in, no install
pktmon start --capture --pkt-size 0 -f capture.etl
pktmon stop
pktmon etl2pcap capture.etl -o capture.pcap

Both tcpdump and pktmon above write a file the tool reads directly, so Wireshark is not required at any point. If Wireshark is available and you would rather work with a capture there first, the steps are:

  1. Move the .pcap file to the machine running Wireshark. On a standalone or air-gapped system this is normally an approved transfer to removable media.
  2. Open Wireshark and choose File → Open, then select the capture. Wireshark reads the tcpdump and pktmon output as-is.
  3. To capture inside Wireshark instead, pick the interface on the start screen and press the blue shark-fin button; press the red square to stop.
  4. To narrow a large capture before importing, type a filter such as ip.addr == 10.20.30.15 into the display filter bar, then use File → Export Specified Packets and choose All packets (Displayed).
  5. Save with File → Save As and choose Wireshark/tcpdump/… - pcap or pcapng. Both formats import.

Wireshark is not installed everywhere and often is not approved on mission systems. Nothing in this procedure depends on it — the native capture tools already produce an importable file.

Capture for long enough to catch periodic traffic. A five-minute capture will miss anything that runs on a fifteen-minute timer.

Only feed it data

Import logs, scans and captures. Documents, instructions and notes are not data sources, and the tool now says so rather than trying to read them. Every parsed row is checked before it reaches the register: both endpoints have to be a real address or hostname, ports have to be numeric and in range, and the protocol has to be one it recognises. Anything that fails is dropped and the count is reported on the import line.

Firepower / FMC reports

If you run FMC, its reports are the single most productive thing you can export, and you do not have to say which is which — the tool works it out from the column names. Export any of these to CSV and drop them in:

ReportWhat it contributes

The detected report type is shown on the import line. If it reads something unexpected you will see it there rather than having to work it out from the rows.

Export as CSV, not PDF. FMC will happily give you a PDF and the tool can recover text from one, but the columns survive far better as CSV.

NetFlow reports in Excel

If your NetFlow analyser gives you a top conversations or top talkers report, export it as .xlsx or CSV and drop it in as it is — title rows, several sheets and a Total line at the bottom are all fine. Endpoints written as hostname (address) are split, ports are pulled out of labels like oracle (1521/TCP), and traffic in MB or GB becomes a byte count. Pick the longest reporting window the analyser offers; thirty days catches monthly jobs that a one-day report misses.

The access control policy as a PDF

If the only form of the policy you can get out of FMC is its printed report, that works. Both of FMC's layouts are read — the wide table with a row per rule, and the per-rule blocks of labelled fields — including wrapped cells and policies that run across several pages. Load your name sources in the same import: where the policy names objects instead of addresses, they are resolved against them.

A CSV export of the policy is still the most reliable form if your FMC version offers one. The PDF reader works from where each piece of text sits on the page, which handles every layout tested so far, but a CSV has nothing to interpret.

Logs that ended up in a PDF

If a log was printed or pasted into a PDF before it reached you, import the PDF directly. The text is pulled back out and run through the normal parsers, so a Zeek conn.log, a firewall connection table or a NetFlow cache all still work. The one case it cannot help with is a scanned page or an image export, because there is no text in the file to recover — you get told that rather than an empty import.

The original text is always better if you can get it. A PDF loses column alignment, and a long line can be re-wrapped in a way no parser can undo.

Firewall connection table

There are two ways to reach the connection table. Use whichever matches your access.

Option A — through Firewall Management Center (usually the easier route). FMC can open a CLI session against a managed device without needing SSH access to the device itself:

  1. Log in to FMC in a browser.
  2. Go to Devices → Device Management and find the device.
  3. Open the device, then use the Threat Defense CLI feature to open a session against it.
  4. Set the command type to show, enter conn all, and run it.
  5. Copy the output out of the results pane into a .txt file.

Option B — direct SSH to the device. Requires network reachability to the management interface and an account on the device:

  1. Start your terminal client and turn on session logging before connecting, so the output is captured to a file. In PuTTY this is Session → Logging → All session output; with OpenSSH use ssh admin@10.x.x.x | tee firewall-conn.txt.
  2. SSH to the management address of the ASA or FTD device.
  3. On FTD you land in the Threat Defense CLI. Enter system support diagnostic-cli to reach the ASA-style prompt, then enable (the password is often blank on FTD — press Enter).
  4. Turn off paging so the output is not broken up by --More-- prompts, then dump the table.

The two commands themselves are on collection card C5 (scripted) or C7 (manual).

Save the captured text and drop it in. Interface names on each line are pulled into the Source Zone and Destination Zone columns, which is what makes the zone-to-zone diagram view useful.

Strip the terminal formatting if you can. A logged SSH session carries ANSI colour and cursor codes alongside the text. The tool removes them on import, but if your terminal offers a plain-text or "printable output only" logging mode, use it — the file will be cleaner and easier to check by eye.

NetFlow cache

The commands are on collection card C6. What matters when you run them:

  • show flow monitor ? lists the monitors that exist on that switch. Nothing listed means NetFlow is not configured there — mark the card N/A and move to the next switch rather than trying to configure it.
  • The CSV form is the easiest to work with. The table and per-record forms import too, so use whichever your platform produces.
  • NetFlow is the only source that sees traffic between two hosts on the same segment, because that traffic never reaches the firewall.

Host connection tables

The commands are on the collection cards at the top — card A2 for Windows, card B5 for Linux. Three things about them are worth knowing:

  • Run them elevated. Without Administrator or sudo the process column comes back empty, and that column is what proves a port is a real listening service rather than a passing connection.
  • Listeners and connections are both wanted. Listeners alone tell you what a host offers; the connections tell you what it actually reaches, which is what the boundary is decided from.
  • PowerShell writes redirected output as UTF-16. The tool detects and decodes that on its own, so there is nothing to convert.

Identify the endpoints

This is the discovery half of PPSM. Flows tell you which ports are in use. The Endpoints panel tells you which systems are on the network, what each one is called, and what it serves.

Every distinct address in the register appears once, with:

  • The role it plays (Server, Client, or Both)
  • The services it answers on
  • How many flows and distinct peers it has
  • Which collector observed it

Rows for unidentified systems are tinted and carry an input box — type a hostname into it and the name is applied across every matching row at once.

Internal and external are scored separately

  • Internal addresses (RFC1918 by default, plus any extra ranges you set in Settings) must be identified by hostname.
  • External destinations are documented by service and purpose instead — a public web address has no internal hostname and is not counted against you.

The counter at the top reads "% of internal systems identified", and the target is 100%.

The work-list round trip

The fastest way to close out discovery when you do not own the naming data:

  1. Export the Unidentified Work List. It contains only internal systems with no name, with blank Hostname and Owner columns.
  2. Send it to whoever runs the network or owns the systems.
  3. Load the completed file back in with Load Host Inventory.
  4. The names resolve across the whole register at once.

A system that shows up in traffic and that nobody can name is itself a finding. Do not quietly drop those rows — they are often the most important thing the exercise surfaces.

A zone called "outside" does not mean the internet. On an enclave firewall it usually means "toward the enclave gateway". So the zone tells the tool which way the traffic is going and the address tells it how far: a private address behind an outside interface becomes B12, and only a genuinely public one becomes B14. Two internal addresses that your subnet map places in different enclaves are not internal-use-only either, because that traffic crosses the enclave gateway.

Mission Justification, CAL status and Assurance Category are left alone on purpose. Those are determinations you make and defend, not things to infer from a port number. Assurance fills only from a service map you supply yourself.

7

Set the boundary, then check the CAL

Boundary is the field a reviewer looks at first. Most of it is already filled in by the time you get here, and most of it will say Internal.

Internal traffic gets no B number. Per the PPSM boundary definitions, internal means not crossing any CAL-defined boundary — and that explicitly includes the Enclave Gateway (B11/B12) and the Enclave DMZ (B9/B10). Traffic that stays inside is tagged Internal, which is a real value rather than a missing one. Do not go looking for a B number to put there.

The tool never assigns a DISN boundary on its own. B1–B8 and B15 describe traffic crossing the DISN, and nothing in host output, a firewall connection table or a NetFlow cache can prove that a flow did. Those are yours to set where the architecture warrants it, and to confirm with your AO or ISSM.

What gets derived:

What the addresses showWhat you get
Both ends inside your rangesInternal — no B number, no CAL lookup, no submission
Inside reaching an address outside your rangesB14 — Enclave GW to External (out)
Outside reaching inB13 — External to Enclave GW (in)
Anything it cannot tellLeft blank for you

If your enclave uses address space outside RFC1918, set Internal ranges under Settings before importing. Without it, traffic that is really internal reads as leaving the enclave and picks up a B14 it does not deserve.

Set the rest by hand where they apply. The full B1–B19 set is in the dropdown, and the review checks flag any internal flow that has ended up carrying a DISN boundary.

How the sources fill each other's gaps

No single source has the whole picture, so the tool reads them against each other. A ruleset knows what is permitted but not who used it; traffic knows who but not what authorises it; a scan knows the hostnames.

GapFilled from
A rule written against a network, so no specific sourceThe host that actually used it, with its hostname and source port, once traffic confirms which one
An observed flow with no authorising rule recordedThe matching rule, written into the Interconnection / Agreement Ref column
An address with no hostnameAny name source that knows it — AD, DNS, hosts file, a scan
A rule nobody usedNothing. It keeps its network and no source port, because nothing observed it, and the review checks flag it instead

Anything derived from an endpoint — enclave, boundary, the eMASS connection points — is recomputed once that endpoint is filled in, so a value worked out from a gap does not survive the gap being closed.

Then check the CAL

Only flows that actually cross a boundary need this. Look the service up on the PPSM CAL before registering: if it is already listed, cite its VA report rather than raising a duplicate, which is the single most common reason a submission comes back. Internal rows need no CAL reference, no assurance category and no submission path, and the review checks no longer ask for them.

8

Run the review checks

The PPSM Review Checks panel runs the register against what submissions actually get sent back for, sorted by how much trouble each one causes.

Two of them only appear once you have imported a ruleset alongside the traffic, and they are the most useful pair in the list:

  • Rule permits traffic that was never seen — either the collection missed it, or the rule is stale and should go forward for removal. Least functionality means the ruleset should not be wider than the traffic needs.
  • Observed traffic with no rule behind it — either a ruleset is missing from your collection, or the traffic is taking a path nobody authorised.
  • Must fix — no boundary set; a destination port in an ephemeral range; no CAL or VA reference cited; anything marked Red or Banned.
  • Should fix — no data service identified (the CAL is organised by service, so a bare port number cannot be matched to anything); no assurance category; no mission justification; HTTP or HTTPS on a non-standard port, which needs an NSPU exception; B13 or B14 with no waiver noted.
  • Worth a look — unnamed internal destinations, and duplicate registrations.

Export Findings writes the whole list to CSV with the offending rows attached, so it can be worked through away from the tool and handed to whoever owns each system.

Import defaultsDefault enclave and collector, pre-filled on every import.

Troubleshooting

Select a symptom for the cause and the fix.

File imports as 0 entries

Almost always the wrong export format — nmap normal output instead of -oX XML, or a Tenable CSV/HTML instead of .nessus. The popup names the specific problem.

"N entries · 0 shown"

A filter is hiding the rows. Clear the search box and the dropdowns, and check you are not on a later page. The data is there.

Nothing happens on drop

Not a real browser tab — a preview pane, document viewer, or Protected View. Confirm the address bar shows file:// and reopen in a browser.

"Could not be read"

File is locked, open elsewhere, on a restricted path, or blocked by endpoint policy. Copy it to a local folder you own.

Capture imports as binary error

The file is probably gzip-compressed (.pcap.gz). Decompress it first. Compressed captures are not read directly.

Huge capture is slow

Lower Max packets to read, and raise Minimum packets per flow, in Settings.

Client and server look backwards

The capture had no TCP handshake to learn from, so the port heuristic guessed. Adjust the well-known port ceiling, or fix the affected rows with bulk-apply.

Diagram is empty or stale

It is generated on demand. Click Generate / Refresh after importing or editing.

Identification coverage looks too low

Your enclave probably uses address space outside RFC1918, so internal systems are being scored as external. Add the ranges under Settings → Internal ranges.

Host inventory file learns nothing

It needs both an IP column and a name column. If the names were already known the tool says so rather than counting them again.

Hostnames did not fill in

Load Host Inventory resolves at load time. After importing more flow data, click Resolve Hostnames to apply the inventory to the new rows.

If something still is not working, run Self-Test. If it comes back green the tool is fine and the problem is the input file; if it comes back red, note the browser and version and which checks failed.
